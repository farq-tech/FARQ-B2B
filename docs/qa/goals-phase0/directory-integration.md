# ربط التوسيع بدليل الجهات — 2026-10-12

## المنفذ وحدود التنفيذ

أصبح توسع CPO إلى حبوب القهوة والأكواب الورقية قابلًا للاستخدام مع دليل فرق بناء في بيئة معزولة. لم ننسخ خوارزمية Ontology أو Supplier Matching جديدة، ولم نعدل مستودع فرق بناء أو مساراته أو بيانات الإنتاج.

`build-unified-cpo.mjs` يولد JSON وحزمة resolver من خوارزمية CPO الأصلية نفسها، مع manifest لبصمة الملفات ومصدرها. `directory-goals.cjs:unifiedPort` يتحقق من سلامة الحزمة ومصدرها ويستدعي `construction-port.cjs:createConstructionPort` مع resolver موحد؛ سلطة `line-intent-authority.serverResolver` الأصلية تتحقق من تطابق النسخة ومساحة المعرفات مع `procurement-ontology-port` الأصلي. يجب تعيين مسار البيانات قبل استيراد الوحدات في عملية جديدة.

النسخة الموحدة المحلية: `cpo-v27-goals-experiment-1`. هذا توحيد المستهلكين المعزولين فقط؛ نسخة واجهة فرق بناء v11 وإنتاج Backend v27 لم تتغير. لا ادعاء بأن توحيد الإنتاج أو ترحيل جميع الواجهات اكتمل. الملفات المولدة مستبعدة من Git وتعاد توليدها بالأمر أدناه. مفردات التوسيع تحتاج اعتمادًا قبل الإنتاج.

## خريطة الاستدعاء الفعلية

- `directory-goals.cjs:createDirectoryGoals().discover` → `construction-port.analyze` → `line-intent-authority.bindLineToIntent` → CPO الأصلي مع بيانات موحدة.
- الشراء والاستفسار → `supabase-repository.createSupabaseConstructionRepository().listEvidenceSuppliers` و`loadSupplierEvidence`؛ استعلامات PostgreSQL الأصلية على `supplier_product_intelligence` و`suppliers` و`supplier_contacts` والأدلة والحظر. معرف `coffee_beans_product` الجديد يصل إلى الاستعلام الأصلي ويسترجع جهة الدليل التجريبية. التوفر يظل غير معلوم.
- التسويق والشراكات → سجل `supplier_profile_facts` الموجود، بنوع `SUPPLIER_INFO` وحالة `OBSERVED` واتجاه علاقة صريح ومالك وصلاحية زمنية. ثم `listReviewCandidates` الأصلي لاسترجاع هويات الدليل المسموح بها. لا كتابة لحقائق المشترين في جداول إثبات بيع المنتجات.
- لا تركيب HTTP أو runtime أو dispatch جديد. التغيير أساس للمرحلة 0 وليس تجربة أهداف كاملة في الواجهة.

## صحة الترشيح

راجعت المصادر الرسمية المنشورة: سلالات تصرح ببيع حبوب القهوة بالجملة، لذا استرجاعها كبائع مناسب للمنتج العام. قائمة بارنز تتضمن مشروبات القهوة، ومنها نستنتج استخدام الحبوب: مرشح محتمل فقط، لا دليل على شراء حبوب المستخدم أو الاستعداد للشراء. مصدر TBA يثبت توزيع القهوة عمومًا؛ لا يحدد حبوب القهوة بما يكفي، لذلك استبعدناه من ترشيحات شراكة حبوب القهوة.

المصادر:
- https://sulalat.com/en/pages/faqs
- https://www.barns.com.sa/en/product/category-products
- https://tba.sa/en

اختبار الاتجاه الإيجابي للشريك يستخدم جهة وهمية واضحة ودليلًا وهميًا في قاعدة الاختبار. يثبت الربط والتصفية فقط، ولا يثبت وجود شريك حقيقي مناسب. طلب الحبوب الخضراء أو المحمصة يمتنع مؤقتًا لأن توافق شكل المنتج لم يثبت؛ لا نقترح مشترين على أساس هوية الحبوب وحدها. لا يوجد عدد نتائج مفروض أو ملء قوائم بجهات ضعيفة.

## ما اختبر فعليًا

اختباران تكامليان على PGlite محلي، باستعلامات المستودع الأصلية وليست إجابات SQL ثابتة. جهات المصادر العامة أعيد بناؤها محليًا بمعرفات وهمية وبريد `example.invalid`؛ ليست نسخة من قاعدة الإنتاج. السيناريوهات: أربعة اتجاهات للمنتج نفسه، نقص الدليل الدقيق للشريك، شريك وهمي إيجابي، عزل المالك، جهة خاصة، أدلة منتهية، حظر المنتج، منتج مختلف، منتج غامض، وشكل منتج غير مدعوم. قارئ قاعدة الاختبار يرفض أوامر الكتابة أثناء الاكتشاف، وoffline guard يمنع الاتصال الشبكي غير المحلي. إعداد البيانات قبل الاختبار محلي فقط.

مولد CPO يتحقق من 768 عبارة أصلية دون تغير نتيجة. نتائج الاختبارات الجديدة في `directory-tests.txt` واختبارات إعادة الاستخدام في `reuse-tests.txt`.

## قبل ← بعد وما بقي

قبل: التوسيع تجربة ذاكرة، ومعرفاته بلا اختبار استرجاع عبر دليل الجهات.
بعد: حزمة موحدة متحققة البصمة، ومعرفاتها تصل إلى استعلامات الدليل الأصلية، مع فصل دليل البيع عن الاستخدام والتوزيع.

باقي للاعتماد: دليل حقيقي دقيق لشريك الحبوب، مراجعة مستقلة لصحة الترشيحات، تأكيد استعداد المشترين أو قبول الشركاء عند الحاجة، إثبات التغطية الجغرافية، واعتماد مفردات التوسيع. قارئ اتجاهات المشترين والشركاء محدود بأول 100 جهة من صفحة الدليل ويعلن وجود صفحات إضافية؛ ليس بحث تغطية شاملة للإنتاج. لم نختبر سلسلة `matchSuppliers` الكاملة أو بيانات الإنتاج الفعلية هنا، ولم نوحد نسخ الإنتاج أو ننشر أو نرسل. لذلك المرحلة 0 ليست READY للانتقال التلقائي للمرحلة 1.
